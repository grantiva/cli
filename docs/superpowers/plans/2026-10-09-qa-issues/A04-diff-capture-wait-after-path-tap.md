# Wait for the screen to settle after each path tap before `diff capture` screenshots

Severity: wrong-result
Platforms: ios, android
Found by: AND-F15 (matrix rows AND-085; MCP AND-096)
Binary: grantiva 2.0.1 (commit c8dc86d), runner 1.1.18-grantiva.7+android-drivers-2, emulator-5554 (Pixel_8_API_35, API 35)

## Expected
Each capture shows the screen its `path` leads to. Source: docs/android.md §Captures and baselines; README §Visual
regression (`screens:` paths).

## Actual
Three `diff capture --no-build` runs with screens Home (launch), Deep Links (tap "Deep Links"), Favorites (tap "Favorites"),
all exit 0. In two of three, `Deep%20Links.png` is byte-identical to `Home.png` (md5 51b8e928...), i.e. the Landmarks list:
```
    ✓ Tap on "Favorites"
Captured 3 screens in 6.5s
  • Home (128.1 KB)
  • Deep Links (128.1 KB)
  • Favorites (52.1 KB)
```
`diff approve` then promotes the wrong image as the Deep Links baseline. Animation scales were 0/0/0, so this is a missing
settle wait, not an animation. MCP `grantiva_tap`'s "Updated hierarchy" was stale the same way once (AND-096).

## Suspected cause
Sources/GrantivaCore/Runner/FlowGenerator.swift:37-39 emits `- tapOn: "<label>"` and :62 then `- takeScreenshot` with no
wait between them; a settle wait is emitted only for an explicit `wait:` step (:47-51). The runner's tap returns once the
click is dispatched, before Compose renders the new destination. Generated by RunnerSession.swift:45 (`writeTemp`).

## Acceptance criteria
- Re-running the repro 10 times: Deep Links hash never equals Home's.
- FlowGenerator emits a settle step (`waitForAnimationToEnd` with a bounded timeout, or the runner's wait-for-idle) after
  every `tap`/`swipe`/`type` and before each `takeScreenshot`; or the capture waits until two consecutive hierarchy
  dumps match. Note any added latency in CHANGELOG.
- GrantivaCoreTests/FlowGeneratorTests: a screen with `path: [tap: "X"]` generates a settle step between `tapOn` and
  `takeScreenshot`.
