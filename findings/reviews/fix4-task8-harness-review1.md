# Task 8 smoke-helper static review

Review scope: `task-8-brief.md`, the two preparation reports, the complete 897-line `task-8-harness-review.diff`, the resulting files under `task-8-harness/`, the controller notes, the binding acceptance inventory, and the named retained fix4 harnesses. This was a static review only. I did not build, run a helper, query or alter a device, or edit product source. The accepted candidate/upgrade, docs/output, and final cleanup placeholders remain controller work after Task 7 and are not findings here.

## Verdicts

- **Specification compliance: CHANGES REQUIRED.** The Android, MCP, and lifecycle helpers do not yet implement all assertions required for the final-candidate smoke. Several omissions permit a green `acceptance.json` without the required evidence.
- **Code quality and execution safety: CHANGES REQUIRED.** The helpers are bounded in many useful ways, but lifecycle target ownership is asserted only by caller-supplied labels and failure paths can strand a detached runner. They are not safe to use on devices yet.
- **Live acceptance: NOT ASSESSED.** Static validation cannot grant a live pass.

## Blocking findings before use

1. **Android — owner `prepare_fix4_smoke`: crash correlation can accept an unrelated fatal and uses the wrong clocks/event timestamp.** In `android_runner_smoke.py:44-50`, each run clears logcat and then selects the first line containing `FATAL EXCEPTION`. It never joins the following `Process: com.kylebrowning.landmarks, PID: ...` record to one of the launch PIDs. It then subtracts the device's logcat epoch directly from the host-authored top-level flow `endTime`. The accepted fix4-1 procedure bracketed device/host clock offset because they differed by about 0.4 seconds, and measured fatal-to-decision against the failed `launchApp` command `endTime`; the top-level flow end is later and includes artifact/report work. The present calculation can therefore false-pass on another process's fatal and false-pass or false-fail from clock skew or post-decision capture latency. Retain the relevant fatal block/process identity, prove it belongs to a PID from this launch, bracket clock offset, and correlate that exact event to the failed launch command decision before applying the accepted two-second bound. Keep artifact-capture timing as its separate L61 measurement.

2. **Android — owner `prepare_fix4_smoke`: the four L51 runs prove terminal success, not movement or transport.** `android_runner_smoke.py:52-54` checks only report status and `failed == 0`. The input flows contain before/after screenshots and a final `Mono Lake` assertion, but the helper neither checks that the retained artifacts exist nor measures direction/travel/settling from exact-session hierarchy reads. It also never proves that direction/coordinate/element used held actions while `engine: adb` used the explicit shell path. A candidate that moves by the wrong engine, or whose report omits the required motion evidence, can pass. Add the binding inventory's per-form before/after app hierarchy movement proof and retain/assert the runner routing evidence for held actions versus the one ADB escape hatch.

3. **Android — owner `prepare_fix4_smoke`: L77's package postcondition can false-pass.** `android_runner_smoke.py:58-62` accepts the flow report and then applies `mResumedActivity not in <only lines containing the package>`. That expression does not prove the target package has no live process, and it does not retain a neutral Settings hierarchy. A running background target, or a dumpsys layout that omits `mResumedActivity` on its package line, passes. The controller requirement is target-package absence plus neutral Settings foreground/hierarchy after the literal clearState/bare-stop/not-visible flow. Assert an exact package process query is empty, assert the focused/resumed component is Settings, capture its hierarchy, and preserve the report's intentional-stop/non-crash result.

4. **Android — owner `prepare_fix4_smoke`: final-candidate L79 repetition and surface agreement are incomplete.** `android_runner_smoke.py:64-75` runs each optional/required text/JSON form once, although the binding criterion requires the preserved optional flow at least three times. It copies a ready file but never asserts its values, does not inspect JUnit, does not assert `element_not_found` in the actual runner command error, and does not prove the following required assertion passed for optional and was skipped for required. Its warning check concatenates stdout and stderr, so runner narration on stderr can mask a CLI text or JSON rendering omission—the exact cross-repository defect found during Task 3. Checking only aggregate warned/failed/passed counts and a substring anywhere in combined output can therefore produce a false pass while CLI output, report detail, ready, or JUnit disagrees. Run the required repetition count and explicitly join exit, each CLI surface, report summary, flow detail, ready summary, and JUnit for both optional and required controls.

5. **MCP — owner `prepare_fix4_smoke`: the prepared iOS L66 sequence omits the retained error/retry contract.** `mcp_smoke.py:41-52` covers successful label, identifier, placeholder, quoted-label, back-button/application exclusion, script, and coordinate cases. It has no missing-selector/error case and no retry-success case, although L66 explicitly preserves existing error/retry behavior and the controller requires the entire selector contract. The helper can write `L66FullSelectorSequence` without exercising those legs. Rebind the corresponding IOS-102/B2-K78/D2-36 retained requests and assert their exact error/retry outcomes before naming the sequence complete. The L65 checks and both-platform ten-pair framing checks otherwise implement the stated request counts, large/small size checks, valid JSON parsing, unique response IDs, and ten update notifications.

6. **MCP — owner `prepare_fix4_smoke`: the large-response precondition is not established.** `mcp_smoke.py:53-66` assumes the current hierarchy will make both resource and tool responses exceed 65,536 bytes. The iOS selector sequence happens to navigate, but it never asserts a hierarchy seed/size before the transport batch; Android performs no UI setup at all. A correctly framed candidate can therefore fail solely because the caller's active app state has a small tree. Bind a deterministic large-hierarchy fixture/state on each platform, assert its two response forms exceed the threshold once, then run the ten mixed pairs. Keep the current per-ID size/uniqueness/notification assertions.

7. **Lifecycle — owner `prepare_fix4_lifecycle_smoke`: the helper covers only subsets of the binding controls it claims to re-run.** The following required controls are absent:

   - `startup_interrupt` runs only the plain form once per platform (`lifecycle_smoke.py:195-218`); L72 requires iOS starting-state plain, quiet, and JSON, plus genuine WDA timeout and unprompted runner/WDA-death controls. The ready control also does not assert the iOS hierarchy contents.
   - `absent_app` (`:286-302`) checks launch refusal and app-file restoration, but not absent plain/JSON `--no-launch` skipped/null output, the installed-app skipped control, or the retained D2-08 app-file status/text controls required by L71.
   - `log_cleanup` (`:304-345`) checks only one interrupted run. L78 requires successful, failed, and repeated interrupted runs, exact child absence before each return, another live run remaining unaffected, and the single truthful verbose terminal diagnostic.
   - `force_teardown` (`:366-384`) checks the live forced case only. L73 also requires the genuinely free force no-op, non-force refusal, helper/process-array behavior, and both project and shared-session cleanup.

   These are underlying procedures/assertions, not merely values waiting for Task 7. Add them before the lifecycle helper is eligible for final-candidate execution.

8. **Lifecycle — owner `prepare_fix4_lifecycle_smoke`: supplied names do not establish owned targets.** Validation at `lifecycle_smoke.py:408-429` blacklists two protected UDIDs and one protected AVD name, but never proves that `--android-serial` resolves to `--android-avd`, that the iOS UDID is the newly created smoke simulator, or that either target appears in a controller-owned inventory. Consequently an arbitrary existing simulator/serial can be operated on while the evidence merely labels the AVD `smoke4-android`. Require an explicit ownership manifest created during provisioning and validate live identity against it before the first device command. The Android runner helper's `adb emu avd name == smoke4-android` check is stronger and should be retained, but it likewise needs the controller's creation/ownership record rather than name alone.

9. **Lifecycle — owner `prepare_fix4_lifecycle_smoke`: failures after a detached start can leave owned runner state behind.** `detach_ready` has no `try/finally` around a platform iteration. Once the detached CLI exits successfully, any later failure (hierarchy, report snapshot, stop JSON, PID/forward check) raises without stopping the exact runner or removing its session. Similar assertion failures after observing a runner in `startup_interrupt` can outlive the spawned CLI despite the finally block signaling only the CLI PID. `main` records failed ownership but performs no exact-owned cleanup (`:442-456`). Add bounded cleanup that uses the already verified device-bound runner PID/session and serial-specific forward, records every action, and never touches unowned/global state. Preserve failure evidence before cleanup.

10. **Shared provenance — owners `prepare_fix4_smoke` and `prepare_fix4_lifecycle_smoke`: declared source/runner identities are recorded without verification.** `run_phase.py:79-82`, `android_runner_smoke.py:23`, and `mcp_smoke.py:22` copy caller-provided `source_sha`/`runner_sha` strings into provenance. The Android helper independently hashes its runner binary but never compares that hash to `runner_sha`; the phase runner records the bundle path but no bundle manifest/hash. Lifecycle records current source HEAD but has no expected merged SHA and no packaged-runner identity. Thus a stale or mixed candidate can generate internally green acceptance with authoritative-looking provenance. Before execution, verify merged source HEAD, candidate binary/version, resource-bundle manifest/hash, packaged runner SHA/version, installed upgraded runner identity, and demo source/artifact identity against the single frozen candidate manifest. The future candidate-upgrade phase may own the canonical manifest, but every helper must consume and verify it rather than accept free-form identity strings.

## Non-blocking observations

- `run_phase.py` defaults to validation only, refuses evidence overwrite, unsets the API key for children, and records top-level streams and argv. The explicit `--execute` gate and immutable raw-output pattern are suitable foundations.
- `mcp_client.py` retains every request and raw response line and rejects invalid JSON; `mcp_smoke.py` pipelines mixed resource/tool requests before waiting and checks exactly 20 large replies, ten small replies, and ten resource-update notifications on each platform. No additional transport blocker was found in the reviewed scope.
- The lifecycle helper signals only helper-spawned CLI PIDs and records device-bound runner/log-child PIDs before making ownership claims. The blocker is incomplete identity validation and cleanup on exceptional paths, not use of a broad kill command.

The final candidate, fresh APFS clone, explicit owned targets, unset API key, literal `fix4-8` session, immutable evidence, and absence of global teardown remain mandatory execution-time bindings. This review does not object to their current placeholders; it objects where the executable helpers would still under-prove or unsafely execute the required smoke after those values are supplied.
